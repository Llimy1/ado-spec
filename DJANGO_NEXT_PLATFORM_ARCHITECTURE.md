# ADO Django + Next Platform Architecture

This document is the canonical implementation architecture for ADO v1 after
the platform stack pivot.

It supersedes:

- `NESTJS_MONOREPO_ARCHITECTURE.md` for new ADO platform implementation work;
- `DJANGO_ARCHITECTURE.md`, which remains a historical Django-only draft.

ADO remains a PostgreSQL-centered orchestration control system. The stack pivot
does not change DB single source of truth, state-machine authority, evidence
gates, artifact lineage, outbox, Git safety, public managed-Project monorepo
rules, or human final merge authority.

## 1. Technology Decisions

| Concern | v1 Decision | Boundary |
|---|---|---|
| Backend | Django + Python | API, DB models, admin, auth, state machine, policy, evidence, and orchestration services |
| API framework | Django Ninja | REST `/v1`, request/response validation, and OpenAPI generation |
| UI | Next.js App Router + React | Control Room only; no direct DB or Worker access |
| Database | PostgreSQL | Sole orchestration truth |
| Persistence | Django ORM + reviewed migrations + explicit PostgreSQL SQL | ORM for ordinary relations; SQL for locks, partial indexes, constraints, and queue semantics |
| Worker | Python Worker entrypoint, initially Django management command | DB queue leasing, external runners, local LLM review, and recovery |
| Queue | PostgreSQL Job/JobAttempt/JobOutboxEvent | No Redis, Celery, RQ, Kafka, or cloud queue dependency in v1-alpha |
| Python tooling | `uv`, `ruff`, `pytest`, `mypy` | Backend, Worker, tests, local LLM adapters |
| Frontend tooling | `pnpm` | Next.js, React, Playwright, generated TypeScript client, UI packages |
| Root orchestration | `Makefile` or `justfile` | One command surface across Python and Node tools |
| API contract | OpenAPI generated by Django Ninja | Next consumes generated/checkable TypeScript client |
| Live updates | SSE over Django ASGI | Freshness signal only; REST snapshots remain authoritative |
| Admin | Django Admin | Internal inspection and emergency visibility, not primary Control Room |
| Vector retrieval | pgvector optional later | Never a control-flow dependency |

Explicit v1 exclusions:

- GraphQL as the Control Room API;
- Kafka as the system event bus;
- Redis/Celery/RQ as a required queue dependency;
- direct browser-to-database access;
- using Django Admin as the primary ADO Control Room;
- automatic production migration, deployment, or merge;
- raw provider payloads, secrets, production data, or local worktree paths in
  browser-visible surfaces.

## 2. Monorepo Topology

ADO remains one public platform monorepo. Python and Node have separate package
managers, but one repository-level command surface.

```text
ado-platform/
  apps/
    api/                       # Django project: API, models, admin, auth
      manage.py
      pyproject.toml           # optional app-local Python package metadata
      ado_api/
        settings/
        urls.py
        asgi.py
        wsgi.py
      ado/
        core/
        projects/
        planning/
        components/
        artifacts/
        execution/
        verification/
        reviews/
        policy/
        state/
        audit/
        integrations/
    worker/                    # Python Worker entrypoints and runner adapters
      ado_worker/
    control/                   # Next.js Control Room
      src/
        app/
        features/
        components/
  packages/
    contracts/                 # OpenAPI artifact and generated TS client
    ui/                        # optional Control Room UI components
    design-tokens/             # optional generated token artifacts
  infra/
    docker/
  docs/
  pyproject.toml               # root Python workspace/config
  uv.lock
  package.json                 # frontend/tooling scripts only
  pnpm-workspace.yaml
  pnpm-lock.yaml
  Makefile                     # or justfile
  .env.example
```

The repository may place the Worker inside `apps/api` at first if that keeps
Django imports simpler. The boundary is process-level: API and Worker have
separate entrypoints, environment profiles, secrets, and process identities.

## 3. Process Boundaries

```text
Django API process
  -> validates REST commands and reads
  -> serves OpenAPI and SSE
  -> invokes application services
  -> never runs external agent processes directly

Python Worker process
  -> leases Jobs from PostgreSQL
  -> runs Codex/local model/provider adapters
  -> validates runner output
  -> writes durable evidence through services
  -> never exposes browser command endpoints

Next.js Control process
  -> renders Control Room UI
  -> calls Django REST API
  -> subscribes to SSE
  -> never imports Django models, DB credentials, Worker code, or runner secrets
```

## 4. Django App Responsibilities

Recommended Django apps map to the canonical DB domains:

| Django app | Owns |
|---|---|
| `core` | Actor, SpecLibraryRevision, shared primitives, redaction/hash helpers |
| `projects` | Project, Repository, Component, EnvironmentProfile, ProjectConstraintProfile |
| `planning` | Roadmap, RoadmapSource, FeatureUnit, relations, acceptance criteria, human checklist definitions |
| `components` | ComponentWork, scopes, contracts, allowed paths, component-work relations |
| `artifacts` | Artifact, provenance, redaction, storage locators, document artifacts |
| `execution` | Job, JobAttempt, WorkerRegistration, outbox, AgentRun, CommandRun |
| `verification` | VerificationProfile, commands, VerificationRun |
| `reviews` | ReviewGroup, ReviewResult, findings, arbiter decisions, revision tasks |
| `policy` | PolicyDecision and policy-rule evaluation services |
| `state` | StateSubject, TransitionRequest, StateTransition, state machine service |
| `audit` | AuditEvent and immutable timeline records |
| `integrations` | Agent ingest, GitHub PR metadata, external-safe adapter records |

Apps expose application services. Views, API operations, admin actions, and
Worker handlers call services instead of mutating orchestration state directly.

## 5. Dependency Rules

Python imports follow this direction:

```text
api views / ninja routers / admin actions / worker handlers
  -> application services in domain apps
  -> models and repositories
  -> core primitives
```

Forbidden dependencies:

- Next.js importing Python modules or reading Django settings;
- Django views importing frontend code;
- Django models running external commands, LLM calls, Git commands, or provider
  API calls;
- Django signals changing core orchestration state implicitly;
- Worker handlers writing `StateSubject.current_status` directly;
- browser code deriving command eligibility locally.

Signals are allowed only for non-authoritative notifications with a named
reason. Core state changes use explicit service methods and transactions.

## 6. Django ORM And PostgreSQL Rules

Django models map the canonical DB model. PostgreSQL remains the authority.

Rules:

1. Every durable model has UUID primary key and UTC `created_at`.
2. Business state lives in `state.StateSubject.current_status`.
3. State changes occur only inside the State Machine service using
   `transaction.atomic()`.
4. The State Machine creates TransitionRequest, PolicyDecision,
   EvidenceGateResult, StateTransition, AuditEvent, and optional outbox rows in
   one transaction.
5. Django model `save()` overrides must not trigger orchestration state
   changes.
6. PostgreSQL-specific partial indexes, check constraints, exclusion
   constraints, advisory locks, row locks, and queue SQL are explicit reviewed
   migrations.
7. `select_for_update(skip_locked=True)` is the default Job lease primitive.
8. Migrations are human-reviewed and never auto-run by Worker processes.

Use Django ORM for ordinary relations and query construction. Use `RunSQL` or
custom migration operations when a PostgreSQL invariant cannot be expressed
safely through Django's high-level migration API.

## 7. API And OpenAPI

Django Ninja is the default API layer.

API rules:

- REST endpoints live under `/v1`.
- Reads and commands are separate operations.
- Routers validate input and call services.
- Routers do not directly update model state for orchestration transitions.
- OpenAPI is generated from Django Ninja schemas and checked in CI.
- Next.js consumes generated TypeScript types/client from the OpenAPI artifact.
- Breaking transport changes require `/v2` or a human-approved compatibility
  plan.

OpenAPI is not an LLM interface. It is the machine-readable API contract
between Django and Next.js.

## 8. Next.js Control Room

The Control Room remains Next.js + React and keeps these documents as binding:

- `CONTROL_ROOM_DESIGN_SYSTEM.md`
- `CONTROL_ROOM_DESIGN_TOKENS.md`
- `CONTROL_ROOM_COMPONENT_SPECS.md`
- `CONTROL_ROOM_PAGE_SPECS.md`

Additional route registry and page-detail specifications may be added as
separate approved Control Room design documents. Until then, the listed
documents are the binding UI implementation baseline.

Next.js responsibilities:

- route rendering;
- responsive UI and accessibility behavior;
- generated API client use;
- SSE freshness handling;
- Playwright and visual QA;
- no direct DB, Django ORM, Worker secret, raw artifact, or raw provider access.

## 9. Python Worker

The v1-alpha Worker starts as a Python process, preferably a Django management
command or a small Python entrypoint that initializes Django settings.

Default command shape:

```text
uv run python apps/api/manage.py ado_worker --worker-id <unique-key>
```

Worker rules:

- one Worker process / one concurrent Job by default;
- leases through PostgreSQL row locks;
- records WorkerRegistration heartbeat;
- runs external tools with bounded timeouts;
- stores stdout/stderr/logs as redacted Artifacts;
- writes runner outputs as claims until validated;
- uses services for state transitions and evidence writes;
- drains on SIGTERM/SIGINT before exit;
- never auto-runs migrations;
- never exposes public HTTP command endpoints.

Celery/RQ may be reconsidered only after PostgreSQL queue behavior is measured
and documented as insufficient.

## 10. Django Admin

Django Admin is allowed for internal inspection and emergency diagnosis.

Admin may:

- view Projects, Feature Units, Component Work, Jobs, Artifacts, transitions,
  and audit records;
- expose read-only search/filter views for operations;
- run narrow service-backed admin actions only when they use the same policy,
  evidence, state-machine, and audit path as the public API.

Admin must not:

- bypass State Machine;
- edit `StateSubject.current_status` directly;
- expose raw secrets, raw provider payloads, raw logs, or production data;
- replace the Next.js Control Room as the primary operator UI.

## 11. Local LLM And Reviewer Adapters

Python is the default integration surface for local reviewer models.

Allowed v1 local reviewer adapters:

- Ollama-hosted Llama;
- Qwen Coder;
- Devstral;
- later adapters only after explicit capability and evidence rules.

Local model output is never evidence by itself. It becomes a ReviewResult claim
and must be validated, deduplicated, and arbitrated before it can affect a PR
or state transition.

## 12. Root Commands

Root commands are stable user-facing intents. Their implementation may use
`uv`, `pnpm`, Django management commands, or frontend scripts.

Recommended command surface:

| Command | Required result |
|---|---|
| `make dev-api` | starts Django API with validated local settings |
| `make dev-control` | starts Next.js Control Room against local Django API |
| `make dev-worker` | starts one Python Worker with a unique worker ID |
| `make lint` | runs Python and frontend lint checks |
| `make typecheck` | runs mypy/pyright where enabled and TypeScript typecheck |
| `make test` | runs deterministic Python and frontend tests |
| `make test-integration` | runs PostgreSQL-backed integration tests in isolated DB |
| `make build-control` | builds Next.js Control Room |
| `make db-migrate` | applies reviewed Django migrations to selected non-production DB |
| `make db-plan` | reports pending migrations/checks without mutating production |
| `make openapi` | generates and checks the OpenAPI artifact |
| `make generate-client` | regenerates the TypeScript API client from OpenAPI |

Do not make `pnpm` the backend orchestrator. `pnpm` is the frontend/package
manager for Next.js and TypeScript tooling.

## 13. Bootstrap Impact

The existing NestJS A1/A2 implementation is now historical implementation
evidence, not the target architecture. New platform bootstrap work starts from
this document.

Recommended reset path:

1. keep `ado-spec` history and approved governance documents;
2. create a new `ado-platform` branch from `integrate`;
3. replace Nest API/Worker/TypeORM packages with Django API/Python Worker;
4. keep or recreate `apps/control` as Next.js;
5. generate OpenAPI from Django Ninja and regenerate the TS client;
6. re-implement A1 health/bootstrap on Django;
7. re-implement A2 orchestration domain with Django models and migrations.

## 14. Completion Criteria

The Django + Next pivot is accepted when:

1. no current canonical document requires NestJS, TypeORM, or Turborepo for new
   ADO platform implementation;
2. Django API, Python Worker, Next Control, PostgreSQL, OpenAPI, uv, pnpm, and
   root command responsibilities are explicitly separated;
3. Django ORM/PostgreSQL migration rules preserve DB invariants;
4. Next.js Control Room can be implemented from existing UI specs without
   direct DB or Worker access;
5. Worker execution remains DB-queued, auditable, bounded, and human-governed;
6. Django Admin is limited to inspection and service-backed emergency actions;
7. bootstrap commands and CI checks cover Python, frontend, API contract, and
   integration evidence.
